# Архитектура приложения для консоли

## Текущая структура исходников

`src/lib.rs` экспортирует сервисы, а `src/main.rs` запускает desktop-приложение и обрабатывает аргументы командной строки.

- `app/` — состояние приложения, сеанс захвата, страницы интерфейса, игровой режим, виджеты, тема, клавиши и обложки.
- `capture/` — типы видео, выбор режима, история кадров, доставка кадров, повторное подключение и нативные backends Windows/macOS. Внешний код использует фасад `console_link::capture`.
- `audio/` — устройства, ограниченный аудиобуфер и мониторинг CoreAudio/WASAPI; `equalizer.rs` обрабатывает PCM десятью стереофильтрами.
- `discord/` — Rich Presence, OAuth в `auth.rs` и ограниченный IPC-транспорт в `transport.rs`.
- `catalog.rs` — каталог и ручной поиск игр для Discord, без анализа кадров.
- `monitoring.rs` — ограниченная история реальных FPS и уровня аудио.
- `platform/` — активация существующего окна и геометрия системного окна; используется бинарным приложением.
- `settings/` — пользовательские настройки, проверка формата и атомарное сохранение.
- `color.rs` — SDR-преобразования, нормализация параметров, встроенные цветовые пресеты и CPU-экспорт.
- `app/color_gpu.rs` + `app/color.wgsl` — один GPU-проход видео; `color_page.rs` — регуляторы/пресеты; `color_integration.rs` — предпросмотр, фиксация параметров и PNG.
- `config.rs` — типизированные константы сборки: размеры окна, бюджеты памяти, таймауты, адреса сервисов и ограничения. Значения сгруппированы по подсистемам; пользовательские настройки хранятся отдельно.

Преобразование строки BGRA используется обоими видеобэкендами. Проверка Discord ID общая для профиля, Presence и IPC handshake. Разбор аргументов и декодирование иконки находятся в одном месте в бинарном приложении. Встроенные ресурсы разрешаются относительно `CARGO_MANIFEST_DIR`.

## 1. Назначение и требования

Компактное desktop-приложение на Rust превращает компьютер в экран и аудиовыход HDMI-консоли. Первый проверяемый комплект: Nintendo Switch, MacBook Pro M2 Pro и карта из карточки Ozon с артикулом 3250235987. Второй обязательный сценарий: Windows 11. Репозиторий должен быть публичным в аккаунте Potanull; название пока рабочее: `console-link`.

Пользователь выбрал общий Rust-интерфейс и отдельные платформенные реализации захвата. Веб-интерфейс и внешний медиаплеер не требуются.

### Согласованный объем первой версии

- Понятное подключение: выбор видеоустройства, связанного аудиовхода и поддерживаемого режима.
- Отдельное игровое окно без настроек и уведомлений, пригодное для захвата Discord и OBS; полный экран с сохранением пропорций.
- Целевой режим 1920x1080 при 60 FPS, только если карта его действительно предоставляет. 59,94 FPS хранится как рациональная частота, без округления при выборе режима.
- Выбор аудиовыхода, громкость консоли, mute, индикатор уровня и ручная коррекция синхронизации.
- Скриншоты в PNG.
- Ручной ввод названия игры, сохранение последнего выбора и передача статуса через Discord Rich Presence.
- Демонстрация игрового окна в Discord с картинкой и звуком на macOS и Windows 11.
- Восстановление после отключения устройства без перезапуска приложения.

Запись, повторы, микрофонный микшер, виртуальные аудиодрайверы, прямая отправка эфира, управление консолью, OCR, HDR, 4K и 120 FPS в первую версию не входят.

### Что известно о карте

В предоставленных пользователем характеристиках продавец заявляет 1920x1080, HDMI, USB 2.0/3.0 и Type-C. Частота кадров, чип, форматы, UVC/UAC и реальная скорость USB не подтверждены. Наличие разъема Type-C не доказывает USB 3.0. В проверенной среде карта пока не обнаружена.

Приложение перечисляет реальные режимы устройства. При отсутствии 1080p60 показывает доступные варианты, например 1080p30 или 720p60, и предлагает выбрать. Оно не выдает дублированные кадры за настоящий захват 60 FPS. Работа через системные API предполагает, что ОС видит карту как поддерживаемое видео- и аудиоустройство; специфический драйвер продавца может потребовать отдельного решения.

### Нефункциональные требования и предлагаемые цели

Эти числа являются инженерными целями, а не подтвержденными свойствами текущей карты:

- Не накапливать неограниченную очередь кадров. При перегрузке отбрасывать устаревшие кадры и показывать счетчик пропусков.
- При нулевой пользовательской коррекции ориентир p95 от получения декодированного кадра приложением до отправки на отображение: до 2 периодов входного кадра. Это метрика приложения, а не HDMI-to-display latency.
- Полную задержку измерять отдельно внешней камерой/таймкодом. Без измерения не обещать миллисекунды.
- На согласованном тестовом оборудовании провести 30-минутный прогон; ориентир остаточного A/V рассогласования после калибровки: не более 40 мс без нарастающего дрейфа.
- Не требовать установки GStreamer, FFmpeg или отдельного плеера.
- После потери карты очищать последнюю картинку и аудиоочередь, освобождать устройства и явно показывать состояние подключения.
- Не выполнять файловые операции, выделения памяти, блокировки и сетевые вызовы в realtime audio callback.
- Размер, RAM и CPU измерять в release-сборках. Числовые бюджеты зафиксировать после первого работающего вертикального среза, не выдавая выбор Rust за гарантию экономичности.

Предлагаемая первая матрица поставки: macOS 13+ arm64 и Windows 11 x86_64. Intel Mac и Windows ARM не считаются проверенными без отдельных сборок и аппаратной приемки. Нижняя граница macOS связана также с официальной поддержкой передачи аудио Discord.

## 2. Выбор технологий

### Выбранное направление

| Компонент | Выбор | Причина и цена |
|---|---|---|
| Язык | Rust stable, версии закрепляются при реализации | Общая логика и интерфейс, изоляция unsafe в платформенных границах |
| UI и окна | egui/eframe с wgpu | Rust UI без WebView, несколько окон, GPU-отрисовка; внешний вид требует отдельного оформления |
| macOS capture | AVFoundation через objc2 framework bindings | Системные устройства, форматы, video/audio sample callbacks; необходимо корректное владение Objective-C объектами |
| Windows capture | Media Foundation через windows-rs | Перечисление устройств и media types, асинхронный Source Reader; COM lifecycle и потоки требуют явного контроля |
| Аудиовывод | CoreAudio на macOS, WASAPI shared mode на Windows | Выбор устройства и системные часы воспроизведения; системный mixer может добавлять задержку |
| Отображение | Общий wgpu renderer | Металл/D3D через backend wgpu. Первая версия может копировать кадр; zero-copy не обещается |
| PNG | ImageIO на macOS, WIC на Windows | Системное кодирование снимка без подключения большого codec runtime |
| Discord | Неблокирующий адаптер документированного desktop IPC | Без обязательной учетной записи в нашем приложении и без bot token |
| Настройки | Версионированный локальный JSON | Нет сервера, базы данных и сетевой синхронизации |

## 3. Минимальные архитектурные приемы

- Платформенные адаптеры изолируют устройства, callbacks, владение ресурсами и unsafe. Общая логика не зависит от COM или Objective-C.
- Явная машина состояний сессии исключает одновременные повторные открытия карты и гонки при отключении.
- Ограниченные потоки данных отделяют realtime audio, callbacks захвата и UI. Каналы управления не используются для передачи каждого пикселя.

Отдельные сервисы, плагины приложения, универсальный media graph и DI framework не требуются. Для проверок достаточно подменяемых источника кадров, аудиочасов и сохранения настроек.

## 4. Компоненты и поток данных

```text
                       Control window (egui)
                     devices / audio / game
                              |
                         Session control
                  state + generation + settings
                              |
              +---------------+---------------+
              |                               |
       macOS native adapter             Windows native adapter
       AVFoundation                     Media Foundation
              |                               |
              +-------- normalized media -----+
                          |              |
                 Video frames         PCM + timestamps
                          |              |
                 bounded frame queue  bounded audio ring
                          |              |
                 sync scheduler       gain / mute / meter
                          |              |
                     wgpu renderer    CoreAudio / WASAPI
                          |              |
                     Game window      chosen output
                          |              |
                          +------ Discord/OBS capture

Game name -> Discord adapter -> local desktop Discord
Displayed frame -> screenshot worker -> PNG file
Settings -> atomic JSON write
```

### Интерфейс и состояния

Окно управления содержит карту, аудиовход, формат, аудиовыход, громкость/mute, индикатор уровня, коррекцию синхронизации и название игры. Во время первоначального подключения показывает последовательность: карта видна, видео получено, аудиовход выбран, звук воспроизводится. Если системные идентификаторы позволяют связать видео и аудио одного USB-устройства, приложение предлагает пару. При неоднозначности выбор делает пользователь; первый попавшийся микрофон не выбирается автоматически.

Игровое окно показывает только изображение с полями по пропорциям. Настройки, статус Discord и ошибки остаются в окне управления. Скриншот сохраняет изображение игры без рамки, курсора и интерфейса. Закрытие игрового окна останавливает захват; окно управления остается открытым. Закрытие приложения освобождает все ресурсы. Горячие клавиши действуют в окнах приложения, глобальный перехват не нужен.

Состояния: `Idle`, `Opening`, `Running`, `Disconnected`, `PermissionDenied`, `UnsupportedMode`, `Error`, `Stopping`. Каждое открытие получает generation ID; запоздавшие callbacks предыдущей сессии игнорируются. Start/Stop идемпотентны. Неподдерживаемый запрос не заменяется молча другим режимом.

### Видео и декодирование

Перечисление режимов сохраняет размер, rational FPS и pixel/media format. Предпочтение получает формат, который одновременно поддерживают устройство и системный путь преобразования. Конкретный порядок NV12/YUY2/MJPEG выбирается измерением на карте, а не предположением о ее чипе.

AVFoundation запрашивает поддерживаемый выходной pixel format. Windows использует Media Foundation Source Reader и доступные системные декодеры/преобразователи. Если камера отдает MJPEG, проверяется получение декодированных кадров системным путем. Если такого пути нет, этот формат помечается неподдерживаемым; собственный декодер и большой codec pack не добавляются незаметно.

Первый renderer копирует доступные raw planes в GPU textures: BGRA напрямую, NV12/YUY2 с соответствующим YUV shader. Учитываются stride, plane layout, color matrix, range и ориентация, а не только ширина и высота. CPU RGBA fallback допустим для неподдержанного формата после измерения расходов. Native texture interop вводится только при доказанном узком месте. Захват не блокируется отрисовкой. При нулевой задержке видео используется короткая очередь; scheduler выбирает самый свежий кадр, срок показа которого наступил. При отрицательной коррекции аудио включается ограниченная история видео с PTS, достаточная для заданной задержки плюс небольшой запас. Кадры до целевого PTS удаляются только после выбора подходящего; очередь имеет одновременно лимиты времени и памяти. При достижении лимита уменьшается фактически достижимая коррекция с явным сообщением, а не молча меняется синхронизация. Screenshot worker получает отдельное владение снимком, а не удерживает буфер драйвера на время записи файла. Преобразование цвета снимка совпадает с игровым renderer.

Версия wgpu выбирается совместимой с eframe/egui-wgpu; независимое обновление до latest может создать несовместимые типы Device/Texture. Framework symbols Apple проверяются на availability относительно macOS 13; новые symbols не вызываются без runtime guard.

### Часы, звук и синхронизация

Видео и аудио могут появляться как разные устройства с независимыми clock domains. Адаптеры сохраняют исходные timestamps и монотонное время получения; общий слой строит сопоставление с монотонной шкалой приложения. Простое равенство timestamps двух устройств не предполагается. Ненадежные timestamps помечаются в диагностике.

Аудиовывод задает темп потребления. Кольцевой буфер ограничен; стартовый target buffer выбирается по стабильности устройства. Небольшой длительный дрейф компенсируется корректировкой коэффициента ресемплинга в платформенном конвертере; разрывы timestamps и смена устройства вызывают контролируемый сброс и повторную синхронизацию. Наличие нужного converter API и диапазон коррекции проверяются в первом media-срезе.

Предлагаемый диапазон ручной коррекции: от -500 до +500 мс. Положительное значение задерживает звук; отрицательное задерживает видео. UI явно подписывает направление. Коррекция увеличивает задержку соответствующего потока; отрицательная задержка физически не создается. Память очередей ограничивается максимальной выбранной коррекцией и небольшим запасом. При нулевой коррекции scheduler не задерживает видео сверх выбранного короткого окна синхронизации.

Индикатор показывает post-gain/post-mute peak с коротким удержанием. Gain 0-100%, без усиления выше исходного уровня. Mute не останавливает capture, но выводит нулевой PCM. При underrun выводится тишина и увеличивается счетчик, а не воспроизводится старый звук.

Ручной A/V offset остается доступным даже при ненадежных timestamps. Автоматическая оценка drift не должна маскировать постоянное рассогласование карты: оно калибруется пользователем и проверяется тестовым сигналом.

### Discord и OBS

Видео и аудиовывод живут в одном процессе с игровым окном. Windows использует shared audio mode; эксклюзивный вывод не входит в первую версию. Приложение не запускает внешний плеер и не создает виртуальный драйвер.

Discord официально поддерживает передачу аудио приложений на macOS 13+ и Windows desktop. Наше приложение не управляет Go Live: пользователь выбирает игровое окно в Discord. Разрешение Screen & System Audio Recording получает Discord, а разрешения на доступ к capture-видео/аудио получает наше приложение по требованиям ОС. Сам факт работы локального звука не доказывает, что звук слышен друзьям.

Первая версия не разделяет громкость «для себя» и «для друзей». Ожидаемое поведение: Discord получает воспроизводимый приложением звук после gain/mute; особенности фактического capture проверяются в звонке. Если пользователь хочет независимый звук для трансляции, это отдельное расширение.

Rich Presence: пользователь вручную вводит игру, явно включает передачу активности. Нужен зарегистрированный Discord Application ID, который не является секретом. Адреса IPC фиксируются адаптером для поддерживаемых платформ. Конкретная библиотека IPC пока не выбрана: предпочтителен поддерживаемый готовый crate после отдельной проверки вместо самостоятельного воспроизведения протокола. Если рабочий готовый вариант не найден, решение выносится на этап реализации, без подмены неофициального API официальным SDK.

Минимальное обещание статуса: введенное название игры присутствует в activity details и показывается продолжительность сессии. Верхнее название активности зависит от поддерживаемого API клиента и проверяется отдельно. При выключенном Discord или запрещенной активности захват продолжает работать. Reconnect ограничен backoff, UI не блокируется. По Stop, отключению карты, выключению интеграции и штатному выходу presence очищается. После аварийного выхода очистка зависит от поведения Discord при разрыве IPC.

OBS захватывает игровое окно и звук приложения стандартными источниками OBS. Полноценная интеграция/плагин OBS не требуется.

### Ошибки и восстановление

- Нет разрешения: конкретное объяснение и путь к настройкам ОС, без бесконечных повторов запроса.
- Устройство занято: показать выбранную карту и предложение закрыть приложение, которое ее использует.
- USB disconnect: остановить звук, очистить изображение, закрыть session и ждать возвращения идентификатора устройства.
- Автовосстановление включается только для ранее выбранного устройства. Повторные открытия ограничиваются backoff; ручной Stop отменяет все ожидающие попытки.
- Потеря аудиовыхода: не переключать звук неожиданно на динамики. Поставить вывод на паузу и предложить выбрать выход.
- «Нет HDMI-сигнала» показывать только при надежном сообщении драйвера. Черный кадр сам по себе не доказывает отсутствие сигнала.
- Ошибка PNG/места на диске: показать ошибку в окне управления, захват продолжить.

## 5. Локальные данные и безопасность

Сервер и БД не нужны. Настройки хранятся в штатном per-user каталоге приложения, скриншоты в выбранной папке изображений.

JSON содержит `schema_version`, идентификаторы видео/аудиоустройств, режим, выбранный выход, громкость, mute, sync offset, последнее название игры, флаг Discord и геометрию окон. Запись: временный файл, flush и atomic replace. Сбой чтения сохраняет поврежденный файл отдельно и загружает безопасные значения по умолчанию. Будущие версии мигрируют только известные схемы; неизвестную новую схему не перезаписывают.

Серийные номера, аудио, кадры и содержимое игры не отправляются в телеметрию. Телеметрия отсутствует. Диагностический отчет экспортируется пользователем и исключает серийные номера, имена пользователя, абсолютные личные пути и содержимое кадров. Discord получает только явно включенную игровую активность. Bot token и OAuth secret не нужны.

Предлагаемая лицензия собственного кода: MIT; окончательный выбор фиксируется перед публикацией. Native frameworks поставляются ОС. Rust dependencies проходят проверку лицензий по точным версиям и lockfile. Подпись/notarization macOS и code signing Windows требуют учетных данных владельца; неподписанный тестовый архив нельзя выдавать за готовую подписанную поставку.

## 6. План реализации, готовый для TDD

План задает порядок, но не означает, что эти шаги уже выполнены. Платформенные FFI вызовы подтверждаются интеграционными и аппаратными проверками, а не имитациями API.

1. **Модель устройств и режимов.** Тест фиксирует точные 60/59,94 FPS, выбор только доступного формата и явный fallback; зависимости: нет.
2. **Машина сессии.** Тест фиксирует Start/Stop, disconnect и игнорирование старой generation; зависит от 1.
3. **macOS enumerate и один видеокадр.** Hardware check подтверждает доступные устройства/режимы и владение sample buffer; зависит от 1-2.
4. **Windows enumerate и один видеокадр.** Проверка на Windows подтверждает COM lifecycle, реальные media types и source reader callback; зависит от 1-2.
5. **Ограниченная очередь видео.** Тест с медленным потребителем подтверждает удаление устаревших кадров и счетчик потерь; зависит от 2.
6. **Игровое окно и renderer.** Интеграционная проверка тестового кадра подтверждает пропорции и отдельное чистое окно; зависит от 3-5.
7. **Аудиокольцо и управление.** Тесты с известным PCM подтверждают gain/mute, индикатор, underrun и ограниченность памяти; зависит от 2.
8. **macOS capture audio и CoreAudio output.** AVFoundation AVCaptureAudioDataOutput получает звук выбранного входа карты; адаптер нормализует PCM и timestamps, обрабатывает discontinuity и смену формата. На Mac проверить, что звук идет именно из HDMI, затем вывод на выбранное устройство, отключение выхода и параметры задержки; зависит от 7.
9. **Windows capture audio и WASAPI shared output.** Отдельный выбранный audio endpoint карты открывается через WASAPI capture; его связь с видеоустройством хранится в настройках. Нормализация PCM, timestamps, silent packets, discontinuity и смена формата проверяются отдельно от renderer. На Windows подтвердить звук именно HDMI и вывод на выбранное устройство; зависит от 7.
10. **Clock mapping.** Тест независимых искусственных clock domains подтверждает перевод времени и сброс при discontinuity; зависит от 5,7.
11. **Ручная синхронизация.** Тесты обеих полярностей offset подтверждают направление и границы буферов. Непрерывный поток 60 FPS и offset -500 мс должен показывать кадры из истории по PTS, а не последний поступивший кадр. Проверить изменение offset и достижение memory limit; зависит от 10.
12. **Drift correction.** Длинный синтетический поток с разницей частот проверяет отсутствие бесконечного роста буфера; аппаратный прогон подтверждает converter path; зависит от 8-11.
13. **Понятное подключение и настройки.** Проверить явный выбор аудиопары, атомарную запись и восстановление состояния; зависит от 3-12.
14. **Скриншот.** Интеграционная проверка PNG подтверждает размеры и отсутствие элементов UI; зависит от 6.
15. **Discord Presence.** Тест адаптера фиксирует включение, обновление игры, reconnect и clear; реальный Discord подтверждает отображение; зависит от 2,13.
16. **Discord screen share.** Два реальных звонка с принимающей стороной, Mac и Windows: проверить видео, звук, выбранные наушники, volume/mute и оконный/полноэкранный режим; зависит от 6,8-13.
17. **Упаковка и публичный репозиторий.** CI fmt/clippy/tests и native build на обеих ОС; инструкции запуска, licenses, известные ограничения, подтвержденная матрица карт; зависит от предыдущих шагов.

### Критерии приемки

- На каждой ОС пользователь подключает карту, видит ее реальные режимы и получает изображение без внешнего плеера.
- Проверены аудиовыход, громкость, mute, индикатор и обе стороны sync offset.
- Проверены USB disconnect/reconnect, отказ разрешения, занятое устройство и потеря аудиовыхода.
- После 30 минут игры не растут очереди; зафиксированы dropped frames, underruns, CPU, RAM и метод измерения задержки.
- Скриншот содержит только кадр игры.
- В Discord на принимающей стороне подтверждены изображение, звук и название игры.
- Windows и Mac считаются готовыми отдельно. Успешная сборка на Mac не подтверждает Windows.

## 7. Открытые вопросы и оставленные исполнителю решения

### Технические проверки до обещания совместимости

- Реальные VID/PID, device IDs, форматы, FPS, аудиопара и USB speed текущей карты.
- Системное декодирование доступного MJPEG и расходы копирования кадра.
- Надежность timestamps, converter drift correction и минимальные устойчивые audio buffers.
- Передача аудио именно этого процесса Discord на обеих ОС, в том числе на выбранный выход и при mute.
- Точные версии crate, MSRV, лицензии и доступность API на нижней границе ОС.
- Регистрация Discord Application ID владельцем и проверка допустимых полей активности.

### Предлагаемые решения автора, пользователь еще не подтверждал отдельно

- Рабочее имя `console-link`, MIT, macOS arm64 + Windows x86_64 как первая матрица.
- Громкость 0-100%, индикатор после gain/mute, sync offset +/-500 мс.
- Отсутствие независимой громкости для локального прослушивания и трансляции.

Эти значения можно изменить при согласовании документа. Цвета, конкретные горячие клавиши, имена внутренних Rust-модулей и точные лимиты буферов оставлены исполнителю в рамках требований. Реализация начнется после согласования этого документа.

## Текущий тракт цветокоррекции(2026-11-11)

В отличие от исторического проекта выше, текущие нативные backends приводят источник к RGB32/BGRA8, после чего передают RGBA8 и timestamp. Матрица, диапазон и HDR-метаданные до UI отдельно не доходят. Цветокоррекция предполагает SDR sRGB; настоящий HDR не заявляется.

При наличии wgpu `session.rs` сохраняет выбранный Arc<VideoFrame> без преобразования в ColorImage. VideoCallback загружает изменившийся источник в Rgba8Unorm, обновляет изменившиеся48байт параметров и рисует в egui-renderpass. Один callback используется либо для видео, либо для отключённой тестовой шкалы. Pipeline/sampler/uniform живут постоянно, texture/bindgroup меняются только при изменении размеров. Last-frame Arc удерживает владение для безопасного ptr_eq. Поверхность sRGB учитывается отдельным флагом; повторное гамма-кодирование исключено.

ColorSettings и пользовательские ColorPreset хранятся в прежнем schema1 settings.json. Новые поля имеют нейтральные defaults; имена и значения нормализуются. Comparison transient и не сохраняется. Экспорт использует пару уже представленного кадра и эффективных параметров. Принудительный original обходит обработку и в экспортном helper. Рендер не ждёт screenshot worker.
