# Переход Console Link на GPUI

## Требования

Цель пользователя - интерфейс на GPUI для Mac и Windows 11. Сохраняются монохромный стиль, отдельный игровой режим, оверлей настроек, три режима окна, клавиши, скрытие курсора, звук, скриншоты, цветокоррекция, NIS/FSR и необязательный RTX на совместимой Windows-системе. Discord, Nintendo и установка компонентов также сохраняются.

Настройки и данные входа не мигрируют: backend и существующий формат настроек остаются прежними. Текущая сборка и PR #4 должны оставаться работоспособными до приемки нового интерфейса.

## Что проверено

- Точный пользовательский источник: https://gpui.rs/.
- Опубликованная версия `gpui 0.2.2`, Apache-2.0; обновлена 30 октября 2026. Для первого опыта следует закрепить точную версию, а не `*` или текущий Git main.
- GPUI поддерживает платформенные окна Mac/Windows. Официальный README предупреждает, что библиотека остается pre-1.0 и API меняется.
- Текущий README Git main уже использует отдельный `gpui_platform`. Его опубликованный пакет при проверке не найден. Код main и документацию опубликованного 0.2.2 нельзя смешивать.
- В Console Link около 8,8 тысяч строк Rust в UI/platform, включая тесты и GPU-код. Размер сам по себе не является аргументом за перенос, но это замена существенной части frontend.

## Главная техническая граница

Текущий тракт:

```text
AVFoundation / Media Foundation
    -> ограниченная очередь VideoFrame
    -> wgpu: цвет / NIS / FSR / RTX
    -> egui callback -> игровое окно и оверлей
```

Требуемый результат:

```text
прежний capture/audio/backend
    -> прежние GPU-проходы
    -> проверенный presenter для Mac/Windows
    -> видео и GPUI-оверлей в одном игровом окне
```

Последняя граница еще не реализована. В GPUI 0.2.2:

- `canvas` и `Element::paint` не дают готового публичного wgpu encoder/pass для вставки нынешнего callback.
- `RenderImage` принимает CPU-изображение. Передача обработанной wgpu-текстуры этим путем потребует чтения результата GPU обратно в память каждый кадр. Такой путь нельзя принимать без измерения задержки.
- Нативный `surface` использует CoreVideo только на Mac. Metal renderer ожидает двухплоскостной NV12 FullRange, тогда как текущий capture выдает BGRA/RGBA.
- Windows `draw_surfaces` в опубликованной версии пуст; общего публичного Windows texture-варианта здесь нет.
- Windows renderer GPUI использует D3D11, нынешний wgpu/RTX путь - D3D12. Доступ к native window handle существует, но сам по себе не доказывает совместимость текстур, синхронизации и оверлея.

Следствие: поддержка окон на обеих ОС не равна готовой интеграции нашего GPU-видео. Существующие шейдеры нельзя перенести заменой импортов egui на gpui.

## Выбранное направление и альтернативы

| Вариант | Польза | Ограничение |
|---|---|---|
| GPUI frontend и сохраненный GPU-presenter | Повторное использование проверенных capture/audio/эффектов | Нужен прототип композиции видео и GPUI на обеих ОС. Рекомендуемый первый эксперимент |
| Перенести эффекты в renderer GPUI или расширить его | Единый frontend/renderer | Поддержка собственного расширения GPUI и отдельная проверка Metal/D3D11/RTX. Пока не выбирать без эксперимента |
| Передавать обработанные кадры через CPU RenderImage | Проще получить первую картинку | Дополнительное чтение GPU и загрузка кадра. Это вариант для сравнения в опыте, а не принятый production-путь |

Полная одновременная перепись backend не нужна. Новые архитектурные слои следует добавлять только там, где эксперимент подтвердит реальную границу.

## Первый этап: технический прототип

Отдельный экспериментальный crate `experiments/gpui-preview`, без изменения основного бинарника, его зависимостей и опубликованной сборки. Сначала синтетический поток Full HD, затем реальная карта при доступном оборудовании. Прототип использует CPU `RenderImage` для базового сравнения. Это еще не доказательство сохранения существующего GPU-видеотракта.

Критерии:

1. GPUI действительно запускается на Mac и Windows 11.
2. Видеоплоскость и GPUI-оверлей работают в одном окне: порядок рисования, события мыши/клавиш, DPI, resize.
3. Проверены ограниченная очередь, освобождение текстур и стабильность памяти при длительном показе.
4. Измерены FPS и время от получения кадра приложением до представления относительно текущего тракта. Это не измерение всей задержки HDMI.
5. Проверены обычное окно, безрамочное окно на текущем мониторе и fullscreen, включая курсор и возврат фокуса.
6. Найден путь для цветокоррекции/NIS/FSR без принятой вслепую дополнительной задержки; Windows RTX остается отдельной обязательной проверкой на совместимом оборудовании.

Реальная карта в предыдущих проверках объявляла максимум 1080p50. Синтетический источник нужен для проверки поведения при 60 FPS; эти два результата нельзя смешивать.

На этом Mac установлен только Command Line Tools, `xcrun --find metal` не находит компилятор. В build.rs GPUI 0.2.2 есть `runtime_shaders`, который обходит предварительную компиляцию Metal. Его можно проверить для локального прототипа. Сборка и запуск этим способом пока не проверены. Для production-сборки следует отдельно проверить обычный путь с Xcode в CI; устанавливать Xcode или переключать системный toolchain автоматически не нужно.

## Дальнейшие этапы после приемки прототипа

1. Отделить существующие GPU-проходы от egui callback, сохранив проверку изображения и производительности.
2. Перенести экран подключения и обнаружение устройств. Проверить независимость медленного аудиопоиска от видео.
3. Перенести звук, изображение и установки компонентов Nintendo. Сохранить неблокирующие операции и отмену.
4. Перенести Discord/Nintendo, обложки и игровые таймеры без изменения авторизации и путей хранения.
5. Перенести игровой оверлей, клавиши, режимы окна и скриншоты. Сверить поведение на обеих ОС.
6. Только после сравнения убрать старый frontend и eframe из поставки. До этого старый путь остается вариантом отката, формат пользовательских данных не меняется.

## Статус

GPUI изолирован в экспериментальном crate. Основной Cargo.toml и пользовательские данные не меняются. Прототип использует прежний native capture backend через библиотеку Console Link, очередь на один свежий кадр и отдельный синтетический источник. Переключение на настоящий источник выполняется явно при запуске, чтобы прототип не открывал камеру без запроса.

Очередь считает полученные и отброшенные кадры. Возраст кадра от callback до обновления UI не является временем до вывода на дисплей и не измеряет задержку HDMI. CPU-путь не включает NIS/FSR/RTX. Эти эффекты остаются в рабочем frontend до проверки общего GPU-presenter.

Закрытие источника посылает отмену без ожидания блокирующего вызова ОС на UI-потоке. Если обнаружение или запуск еще идут, worker проверяет отмену после их возврата и освобождает native session. Весь процесс прототипа не зависит от данных входа Nintendo/Discord и не записывает пользовательские настройки.

Сборка, запуск и результаты измерений фиксируются в README прототипа по мере проверки. Нет оснований обещать меньшую задержку или нагрузку до сравнения на реальном видеотракте.
